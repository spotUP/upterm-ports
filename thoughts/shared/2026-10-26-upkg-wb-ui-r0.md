# R0 result

Verdict: design option (a) (log gadget fed from a pipe in the same Intuition loop) is VIABLE. One caveat: ending a
native child that is still writing needs a Break signal to that process; closing the pipe, SIGINT, SIGTERM and SIGKILL
did not end it (see "Found").

Program: `tests/amiga/ixwbpipe.c` (branch `spike/upkg-wb-ui-r0`, worktree `vtcon/.claude/worktrees/wbui-r0`),
`make build/amiga/ixwbpipe`, run `VTC:ixwbpipe [idle|popen|fork|silent|all] [close]` on rig 7 (`--max`, OS 3.1 kit
Workbench 40.42). Output lines `R0:` also in RAM:ixwbpipe.log.

## What works under ixemul
- `ix_select(nfd, &rfds, NULL, NULL, &tv, &mask)` from `<ix.h>` (library/select.c:554) with the window's
  signal bit (`1L << win->UserPort->mp_SigBit`) in `mask`: one call waits on the pipe AND Intuition. `WaitSelect` is
  bsdsocket's and is not used; plain `select()` has no mask argument. Both the pipe fd and the signal wake it.
- `pipe()` + `vfork()` + `dup2(w,1)`, `dup2(w,2)` + `execvp("List", ...)` of a native AmigaDOS command: its output
  (stdout and stderr) arrives in the pipe, nothing on the console.
- `popen("List SYS:C", "r")` works, `fileno(fp)` can be selected on; EOF detected, `pclose` fine.
- `ioctl(fd, FIONREAD)` on the pipe works (0 failures); max seen 392 = what the pipe holds at that moment.
- `waitpid` after EOF returns the child at once, status 0.
- `getrusage` works but ticks at 10 to 20 ms granularity (CPU figures below are coarse).

## Measured (rig 7, 68060 max, fast host)
R0: popen: 15080 bytes, 250 lines, 74 reads, max read 392, avg 203, polls 75, longest gap between polls 384 us
R0: fork-list: 223100 bytes, 4073 lines, 1122 reads, max read 392, avg 198 bytes per poll, first byte 4.5 ms, longest gap 1280 us, wall 1.2 s, cpu 16 to 30 per cent while a `List SYS: ALL` streams (about 180 kB/s)
R0: idle (no child, 500 ms select timeout): 6 polls in 3 s, all timeouts, cpu below the clock granularity
R0: silent child (Wait 4 SECS, no output): 9 polls in 4 s, 8 timeouts plus the EOF wake; cpu not measurable (idle)
- Bytes per poll: a read returns at most what the pipe holds, about 200 average and 392 max for List (one line
  group per write); no 4096 reads happened, so the log gadget must append in many small pieces, and redraw once per
  loop pass, not per read.
- Close gadget while a child streams (button clicked through wasabi mid stream): IDCMP message age at pickup 0 us (below
  the 1/50 s stamp resolution); the longest gap between two polls during streaming was 0.4 to 2.3 ms. The window answers
  well under the 1 s requirement.

## Found
1. A native child still writing to a pipe whose read end was closed does not end: close(), SIGINT, SIGTERM and
   SIGKILL each waited 2.5 s, waitpid stayed 0 (run 3, child blocked in its write). The first version called
   kill(SIGTERM) then blocking waitpid: the program hung and had to be broken from outside. G3 must not wait for a
   native child after a close request. It needs Signal(child process, SIGBREAKF_CTRL_C) (the process from the
   ixemul pid, or `ixkill`), or the window refuses to close while a run is on (the plan's G3 already says that: keep it).
2. One run ended with the program gone and its window orphaned after the read end was closed with the child still
   running (log stopped after "trying close of the read end only"); the next run with a 1.5 s usleep in front of the
   first waitpid(WNOHANG) did not repeat it. Unexplained, flaky, not chased (budget). Same remedy: never abandon a
   running native child; refuse the close.
3. Log appends: output of an in-process `opkg_cmd_exec` (no child) goes to stdio FILE*, so the plan's D4 needs the
   redirect on fd 1/2 in the upkg process itself (dup2 onto a pipe, drain in the loop), not a child. Not measured
   here: dup2 onto the process's own fd 1/2 and curl's vfork child writing into that pipe. Next spike step.
4. `<intuition/intuition.h>` pulls `devices/timer.h` and its `struct timeval` clashes with ixemul's; include the Amiga
   headers under `#define timeval amiga_timeval` (as in the test).

## Not measured
- Self redirect (dup2 onto the process's own stdout/stderr) with `upkg list` as the source: the rig kit had no upkg
  installed; `List` stands in as a native child writing 200 B chunks.
- GadTools gadgets: plain Intuition window with a close gadget only (the question was the loop).
